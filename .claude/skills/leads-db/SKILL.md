# Хранение заявок в базе

Движок: `engine/salesbot/` (`storage_db.py`, `db/`).

**Не начинай, пока не пройдена Фаза 2.** Бот собран, `config.env` заполнен, приёмник принимает заявки в файлы — тогда есть что дублировать. Не собран — возвращайся к навыку `build-salesbot`.

## Зачем это, если заявки и так сохраняются

Приёмник кладёт каждого человека в файл-карточку. Файл — рабочая память бота: он её читает, дописывает шаг диалога, историю. И он же теряется от неудачного `rsync` или чужой команды `rm` в соседней папке.

База — второй экземпляр, от такого затирания/сноса он защищает. Она ничего не решает в диалоге и никогда не мешает приёму: **карточка-файл первична, база — журнал.** Упала база — заявка всё равно принята, в логе строка «карточка-файл на месте», человек ничего не заметил.

**Это не бэкап.** Том базы стоит на том же диске, что и файлы-карточки — потерял диск целиком, потерял и то, и другое. От потери диска спасает только настоящий бэкап (раздел 6), не дублирование в соседнюю таблицу.

Слой выключен, пока нет `DB_URL`. Пак без базы работает ровно как раньше.

## 1. Подними базу рядом с приёмником

База живёт **на том же сервере**, где приёмник. Не на ноутбуке, не «пока локально» — иначе приёмник будет стучаться в пустоту.

```bash
cd engine/salesbot/db
printf 'POSTGRES_USER=quiz\nPOSTGRES_PASSWORD=<длинный_пароль>\nPOSTGRES_DB=quiz\n' > .env
docker compose up -d
docker compose ps          # health: healthy
```

**Пароль — только буквы и цифры.** Он встаёт в `DB_URL` строкой, а символы `@ : / ?` в нём ломают адрес — база поднимется, а подключиться не выйдет. Придумай длинный и не клади его никуда, кроме `.env` и `config.env`. Оба в `.gitignore`.

Порт в `docker-compose.yml` открыт как `127.0.0.1:5432` — только локальная петля. **Не меняй на `0.0.0.0`.** Postgres с коротким паролем на открытом порту сканеры находят за часы, а внутри — телефоны твоих клиентов.

**Нет docker?** Не обязателен. Есть локальный Postgres (поднятый через `brew install postgresql` / `apt install postgresql`, уже запущенный сервис) — накати схему прямо в него, без контейнера:

```bash
createdb quiztest   # или своя база под тест
psql -d quiztest -f db/schema.sql
```

Дальше `DB_URL` в `config.env` указывает на эту базу (`postgresql://<пользователь>@127.0.0.1:5432/quiztest`), а стык проверяется теми же шагами раздела 4 — разница только в способе поднять базу, дальше всё одинаково.

## 2. Схема

На **свежем** томе схема накатится сама — `schema.sql` смонтирован в `docker-entrypoint-initdb.d`, `docker compose up -d` уже её применил. Проверять руками не нужно.

Ручной накат нужен только на **уже живой** базе (том не пустой, initdb не срабатывает второй раз):

```bash
docker compose exec -T db psql -U quiz -d quiz < schema.sql
```

Так — без `psql` на хосте, через контейнер. Схема идемпотентна — гонять можно сколько угодно раз. Таблица одна, `leads`: код квиза, имя, телефон, класс, дорожка, ответы `jsonb`, воронка, две отметки времени.

## 3. Включи слой

Драйвер ставится отдельно — движок стдлибный, и без базы он не нужен. Ставь **в то же окружение python, из которого запускается `intake.py`** (тот же venv или тот же системный `python3`) — иначе приёмник его не увидит:

```bash
pip install "psycopg[binary]"
```

В `config.env` (не в промпт, не в персону):

```
DB_URL=postgresql://quiz:<пароль>@127.0.0.1:5432/quiz
```

Перезапусти приёмник — переменные читаются на старте:

```bash
LEADS_DIR=~/quiz-leads python3 intake.py 8087
```

Нет драйвера или нет `DB_URL` — слой молча выключится. Это не поломка, это режим по умолчанию.

## 4. Проверь живой заявкой

Проверка засчитывается, только когда сошлись **обе** половины: строка в базе и карточка на диске.

```bash
curl -s -X POST http://127.0.0.1:8087/quiz-submit \
  -H 'Content-Type: application/json' \
  -d '{"quiz_id":"test01","name":"Проверка","answers":{"Q1":"работаю сам","Q2":"ремонт"}}'

psql "postgresql://quiz:<пароль>@127.0.0.1:5432/quiz" \
  -c "SELECT quiz_id, name, klass, answers FROM leads WHERE quiz_id='test01';"
cat ~/quiz-leads/test01.json
```

Пусто в базе, а карточка есть — смотри лог приёмника. Строка «не легла в базу» значит, что слой включён и база отвечает отказом. Тишины в логе нет вовсе — слой выключен: не подхватился `DB_URL` или не поставлен драйвер. Пусто везде — дело не в базе, а в приёмнике.

Отдельно проверь **повторный приход**: пошли тот же `quiz_id` второй раз с телефоном и одним новым ответом. Строка должна **дополниться**: имя и старые ответы на месте, телефон дописан. Затёрлось — схема накатана не та.

Убери тестовую заявку после проверки — **обе половины**, не только базу:

```bash
psql "postgresql://quiz:<пароль>@127.0.0.1:5432/quiz" -c "DELETE FROM leads WHERE quiz_id='test01';"
rm ~/quiz-leads/test01.json
```

Забыл файл-карточку — `test01` останется в счёте фазы «Тест офферов» навсегда (раздел «Как считать» в навыке `offer-testing` считает по файлам в `LEADS_DIR`) и бот однажды поднимет этого фейкового лида по коду `test01`, если кто-то случайно перейдёт по такой ссылке.

## 5. Выведи квиз в интернет

Приёмник ловит заявки, но слать их пока некому: квиз живёт у тебя на машине по `127.0.0.1`, клиент туда не придёт. Три действия — и воронка работает без тебя.

**Выложи папку `engine/quiz` статикой.** Сборки нет, конфиг для Vercel уже лежит рядом — `vercel.json` отдаёт папку как есть. Подойдёт любой хостинг, где `api/quiz.js` **исполняется**, а не отдаётся текстом (serverless-функции). Хостинга с функциями нет — положи квиз на свой сервер под nginx, а `/api/quiz` отправь `proxy_pass` на приёмник: результат тот же.

Прослойка нужна не для красоты. Страница открыта по `https`, приёмник висит по `http` на своём порту — такой запрос браузер из страницы не выпустит (смешанный контент). Прокси ходит сервер-серверу, браузер видит только твой домен.

**Задай переменную окружения `QUIZ_INTAKE_URL`** — полный адрес приёмника, тот самый порт из раздела 3:

```
QUIZ_INTAKE_URL=http://198.51.100.10:8087/quiz-submit
```

Переменная читается на старте функции — задал после выкатки, выкати ещё раз, иначе она не подхватится. Не задал вовсе — прокси отвечает `503`: квиз досматривается до финала, показывает диагноз и запасной код, но **ни одна заявка не доезжает** ни до карточки, ни до базы. Отказ тихий, на экране человека всё выглядит нормально.

**Верни ссылку на бота в `destination.url`.** В `engine/quiz/quiz.config.js` там стоит заготовка со сборки квиза (`https://t.me/example_bot`). Поставь адрес **своего** бота и параметр, которым к ссылке дописывается код: Telegram — `codeParam: 'start'`, ВКонтакте — `codeParam: 'ref'`. Уехала заготовка — кнопка финала уводит людей в чужой диалог, а код квиза не доходит до бота, и разбор начинается с чистого листа, как будто человек ничего не отвечал.

### Пройди путь целиком — с телефона

Не с ноутбука, где всё открыто и залогинено: с телефона, как обычный человек по публичной ссылке.

1. Пройди квиз до финала — диагноз показался
2. Нажми кнопку — открылся **твой** бот, в строке запуска виден код квиза
3. Отправь боту первое сообщение — он узнал тебя и говорит про твои ответы, а не общими словами
4. На сервере сошлись обе половины: `cat ~/quiz-leads/<код>.json` и строка в базе

```bash
psql "postgresql://quiz:<пароль>@127.0.0.1:5432/quiz" \
  -c "SELECT quiz_id, klass, created FROM leads ORDER BY created DESC LIMIT 3;"
```

Слой базы не включал — засчитывается карточка-файл: она первична, база только журнал.

Разошлось — читается по месту обрыва. Диагноза нет вовсе — дело в самом квизе, не в приёме. Диагноз есть, а на сервере пусто — смотри `QUIZ_INTAKE_URL` и логи приёмника (`503` в консоли браузера значит «переменная не задана», `502` — «приёмник недоступен снаружи»). Карточка легла, а бот не узнал — не тот `destination.url` или не тот `codeParam`.

Свою тестовую заявку убери, как в разделе 4: обе половины, и файл, и строку в базе.

## 6. Бэкап

База без бэкапа — та же потеря, только позже. Сначала папка под дампы (её нет по умолчанию — без неё редирект молча падает, и бэкапа не будет, а крон отчитается «успех»):

```bash
mkdir -p ~/quiz-backup
```

Потом одна строка в `crontab -e`, каждую ночь:

```
0 4 * * * cd ~/<папка_с_паком>/engine/salesbot/db && docker compose exec -T db pg_dump -U quiz quiz | gzip > ~/quiz-backup/$(date +\%F).sql.gz
```

Путь в начале обязателен: cron стартует не из твоей папки, а `docker compose` без своего `docker-compose.yml` не знает, что запускать. Знак `%` в cron экранируется — отсюда `\%F`.

Папку `~/quiz-backup` держи **вне репозитория** — там персональные данные. Раз в месяц проверяй, что дамп разворачивается: невосстановимый бэкап хуже отсутствующего, потому что на него надеются.

## После простоя базы — догони журнал

База полежала (переустановка, чистый том, сбой) — журнал отстал от файлов-карточек, а карточка-файл первична, так что это чинится без даунтайма приёмника. Один идемпотентный проход по всему `LEADS_DIR`:

```bash
cd engine/salesbot && python3 -c "import glob, json, storage_db; [storage_db.save_lead(json.load(open(f))) for f in glob.glob(__import__('os').path.expanduser('~/quiz-leads/*.json'))]"
```

`save_lead` — upsert: непустое поле в базе не затирает пустым из файла. Гонять можно сколько угодно раз, в том числе на живой базе для профилактики — вреда не будет.

## Что база не делает

Не заменяет карточки и не читается ботом. Не считает класс и дорожку — они приезжают уже посчитанными. Не чистит старое: закон о персональных данных требует убирать то, что больше не нужно, — раз в квартал сноси заявки, с которыми ничего не будет.

Подробно про то, где эта воронка обычно рвётся, — `playbook/08-грабли.md`.

## Частые ошибки

| Что | Почему плохо |
|-----|--------------|
| Порт `0.0.0.0:5432` наружу | базу с простым паролем находят сканеры, внутри — телефоны клиентов |
| Пароль в репозитории или в промпте | публичный репозиторий, пароль навсегда в истории |
| `DB_URL` с `127.0.0.1`, а база на другой машине | приёмник молча пишет в пустоту, ты узнаешь через месяц |
| База поднята, схема не накатана | каждая заявка тихо падает в лог, в таблице ноль |
| Проверил только базу, карточку не открыл | сломанный файловый слой = бот не узнаёт человека |
| Бэкапа нет либо он в репозитории | либо потеря заявок, либо утечка персональных данных |
| Квиз опубликован без `QUIZ_INTAKE_URL` | прокси отвечает `503`, человек проходит квиз впустую, ты не узнаёшь об этом |
| В `destination.url` осталась заготовка | кнопка финала уводит к чужому боту, код квиза не доезжает |
| Путь проверен только на своей машине | публичная страница ходит по другому адресу, чем `127.0.0.1` |
| Ждёшь, что бот начнёт читать базу | он читает карточку-файл, база — журнал |
